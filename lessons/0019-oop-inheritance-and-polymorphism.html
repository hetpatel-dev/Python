Lesson 19: OOP — Inheritance & Polymorphism

concept Object-Oriented Programming, Inheritance, Polymorphism, super(), MRO, Mixins, ABCs, Duck Typing

Inheritance lets you build new classes from existing ones, reusing and extending code. Polymorphism lets different objects respond to the same interface in their own way. Together, they are the backbone of flexible, maintainable OOP. This lesson covers the official Python tutorial on inheritance, multiple inheritance, and abstract base classes.

Primary sources: Tutorial — Inheritance, Multiple Inheritance, MRO HowTo, abc module, collections.abc, isinstance, issubclass.

1. Introduction to Inheritance

Inheritance allows a new class to adopt the attributes and methods of an existing class. The new class (child/derived) extends the existing class (parent/base) without modifying it.

Why Inherit?

  • Code reuse: Write common logic once in the parent, inherit it everywhere.
  • Specialization: Child classes add or override behavior for specific needs.
  • Polymorphism: Treat different objects uniformly through a shared interface.
  • Logical hierarchy: Model real-world "is-a" relationships (Dog is an Animal).

Basic Inheritance Syntax

class Animal:
    def speak(self):
        return "..."

class Dog(Animal):          # Dog inherits from Animal
    def speak(self):
        return "Woof!"

class Cat(Animal):          # Cat inherits from Animal
    def speak(self):
        return "Meow!"

dog = Dog()
cat = Cat()
print(dog.speak())          # Woof!
print(cat.speak())          # Meow!
print(isinstance(dog, Animal))  # True
print(isinstance(cat, Animal))  # True
💡 "is-a" relationship: Inheritance should model a true "is-a" relationship. A Dog is an Animal. A SavingsAccount is an Account. If the relationship is "has-a" (a Car has an Engine), use composition instead.

2. Single Inheritance

Single inheritance means a class inherits from exactly one parent. This is the most common and straightforward form.

Overriding Parent Methods

A child class can replace a parent's method by defining one with the same name:

class Shape:
    def area(self):
        raise NotImplementedError("Subclasses must implement area()")

    def describe(self):
        return f"Shape with area {self.area()}"

class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius

    def area(self):              # Overrides Shape.area()
        return 3.14159 * self.radius ** 2

c = Circle(5)
print(c.area())                 # 78.53975
print(c.describe())             # Shape with area 78.53975

Adding New Methods and Attributes

Child classes can extend the parent with entirely new functionality:

class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    def greet(self):
        return f"Hi, I'm {self.name}"

class Student(Person):          # Inherits __init__ and greet
    def __init__(self, name, age, school):
        super().__init__(name, age)  # Call parent's __init__
        self.school = school         # Add new attribute

    def study(self, subject):       # New method
        return f"{self.name} is studying {subject} at {self.school}"

alice = Student("Alice", 20, "MIT")
print(alice.greet())            # Hi, I'm Alice (inherited)
print(alice.study("Python"))    # Alice is studying Python at MIT

Using Parent's __init__

Without super(), you must call the parent's method explicitly:

class Employee:
    def __init__(self, name, salary):
        self.name = name
        self.salary = salary

class Manager(Employee):
    def __init__(self, name, salary, department):
        Employee.__init__(self, name, salary)   # Explicit call
        self.department = department

m = Manager("Alice", 90000, "Engineering")
print(m.name, m.salary, m.department)
⚠️ Avoid hardcoding parent name: Using Employee.__init__(self, ...) hardcodes the parent. If you change the inheritance, you must update every such call. Prefer super() instead.

3. The super() Function

super() returns a proxy that delegates method calls to the parent class. It's the recommended way to call parent methods.

super() in __init__

class Animal:
    def __init__(self, name, species):
        self.name = name
        self.species = species

    def __repr__(self):
        return f"{self.__class__.__name__}(name={self.name!r}, species={self.species!r})"

class Dog(Animal):
    def __init__(self, name, breed):
        super().__init__(name, species="Canine")  # Call parent __init__
        self.breed = breed

class Puppy(Dog):
    def __init__(self, name, breed, training_level):
        super().__init__(name, breed)             # Call Dog __init__
        self.training_level = training_level

p = Puppy("Rex", "German Shepherd", "beginner")
print(p)                        # Puppy(name='Rex', species='Canine')
print(p.breed)                  # German Shepherd
print(p.training_level)         # beginner

super() in Other Methods

class Base:
    def greet(self):
        return "Hello from Base"

class Middle(Base):
    def greet(self):
        base_greeting = super().greet()      # Call Base.greet
        return f"Middle says: {base_greeting}"

class Child(Middle):
    def greet(self):
        middle_greeting = super().greet()    # Call Middle.greet
        return f"Child says: {middle_greeting}"

c = Child()
print(c.greet())
# Child says: Middle says: Hello from Base

When NOT to Use super()

  • When you don't want to call the parent method at all (complete override).
  • When the parent's __init__ does setup you explicitly want to skip.
  • When calling a specific parent in diamond inheritance (use Parent.method(self) instead).

super() with Multiple Arguments (Python 3)

In Python 3, super() takes no arguments — it uses magic to find the correct class and instance. In Python 2, you had to write super(ClassName, self). The old syntax still works but is unnecessary.

# Python 3 (preferred)
super().__init__(name, age)

# Python 2 style (still works, but unnecessary)
super(DetailedPerson, self).__init__(name, age)

4. Method Resolution Order (MRO)

MRO is the order Python searches for methods in a class hierarchy. It determines which method gets called when multiple classes define the same method.

Viewing MRO

class A:
    def greet(self): return "A"

class B(A):
    def greet(self): return "B"

class C(A):
    def greet(self): return "C"

class D(B, C):
    pass

print(D.__mro__)
# (, , , , )

print(D().greet())              # B

MRO Rules: C3 Linearization

Python uses the C3 linearization algorithm (also called C3 superclass linearization). The rules are:

  1. Depth-first, left-to-right: Search the first parent, then its parents, before moving to the next parent.
  2. No duplicate visits: If a class appears in multiple paths, it's visited only once.
  3. Monotonic: If class A comes before class B in the MRO of a child, A comes before B in all descendants.
# The diamond problem
class A:
    def method(self): return "A"

class B(A):
    def method(self): return "B"

class C(A):
    def method(self): return "C"

class D(B, C):
    pass

# MRO: D -> B -> C -> A -> object
# NOT: D -> B -> A -> C -> A (A visited only once!)
print(D().method())             # B (first match in left-to-right order)
print(D.__mro__)
# (D, B, C, A, object)

MRO Violations

If the class hierarchy is inconsistent, Python raises a TypeError at class creation time:

# This WILL raise an error:
# class X(Y, Z): pass  # if Y inherits from X and Z inherits from Y
# Python detects the inconsistent ordering and raises TypeError

5. Multiple Inheritance

Multiple inheritance means a class inherits from more than one parent. This is powerful but must be used carefully.

Basic Multiple Inheritance

class Flyer:
    def fly(self):
        return "Flying through the air"

    def describe(self):
        return "I can fly"

class Swimmer:
    def swim(self):
        return "Swimming in water"

    def describe(self):
        return "I can swim"

class Duck(Flyer, Swimmer):
    def quack(self):
        return "Quack!"

duck = Duck()
print(duck.fly())              # Flying through the air
print(duck.swim())             # Swimming in water
print(duck.quack())            # Quack!
print(duck.describe())         # I can fly (first in MRO)

# MRO: Duck -> Flyer -> Swimmer -> object
print(Duck.__mro__)
# (Duck, Flyer, Swimmer, object)

The Diamond Problem

The diamond problem occurs when two parent classes share a common ancestor:

class Device:
    def __init__(self):
        self.on = False

    def toggle(self):
        self.on = not self.on
        return self.on

class Phone(Device):
    def call(self, number):
        return f"Calling {number}"

class Camera(Device):
    def take_photo(self):
        return "Photo taken"

class SmartPhone(Phone, Camera):
    def __init__(self):
        super().__init__()     # Only ONE Device.__init__ is called
        self.apps = []

phone = SmartPhone()
print(phone.toggle())          # True (inherited from Device, via Phone)
print(phone.call("555-1234"))  # Calling 555-1234
print(phone.take_photo())      # Photo taken
print(phone.apps)              # []

# MRO: SmartPhone -> Phone -> Camera -> Device -> object
print(SmartPhone.__mro__)
# (SmartPhone, Phone, Camera, Device, object)
💡 C3 linearization saves the day: Without C3, Device.__init__ could be called twice. C3 ensures each class appears exactly once in the MRO, so super() in Diamond calls each method only once.

When to Use Multiple Inheritance

  • Mixins: Combining independent, reusable behaviors.
  • Interface implementation: A class implementing multiple abstract interfaces.
  • Framework design: Composing orthogonal concerns (logging + caching + auth).
⚠️ Keep it simple: Avoid deep multiple inheritance chains. Two or three parents is usually the maximum that remains understandable. More than that suggests a design problem.

6. Mixins

A mixin is a class that provides methods for other classes but is not meant to be instantiated on its own. Mixins add functionality in a reusable, composable way.

Mixin Naming Convention

Mixins are conventionally named with a Mixin suffix:

class JsonMixin:
    """Mixin that adds JSON serialization to any class."""
    def to_json(self):
        import json
        return json.dumps(self.__dict__, indent=2)

    @classmethod
    def from_json(cls, json_str):
        import json
        data = json.loads(json_str)
        return cls(**data)

class LogMixin:
    """Mixin that adds logging to any class."""
    def log(self, message):
        print(f"[{self.__class__.__name__}] {message}")

class User(JsonMixin, LogMixin):
    def __init__(self, name, email):
        self.name = name
        self.email = email

u = User("Alice", "alice@example.com")
print(u.to_json())            # {"name": "Alice", "email": "alice@example.com"}
u.log("User created")          # [User] User created

Mixin Design Principles

  • No __init__ (or call super()): Mixins should not require specific initialization unless they call super().
  • No state (preferred): Ideally, mixins are stateless and only add methods.
  • Single responsibility: Each mixin does one thing well.
  • Not instantiated directly: Mixins exist to be combined, not used alone.

Practical Mixin Examples

import time

class TimingMixin:
    """Adds timing capability to methods."""
    def time_method(self, method_name):
        start = time.time()
        result = getattr(self, method_name)()
        elapsed = time.time() - start
        print(f"{method_name} took {elapsed:.4f}s")
        return result

class ComparableMixin:
    """Adds comparison operators based on a key method."""
    def _key(self):
        raise NotImplementedError

    def __eq__(self, other):
        return self._key() == other._key()

    def __lt__(self, other):
        return self._key() < other._key()

    def __le__(self, other):
        return self._key() <= other._key()

    def __gt__(self, other):
        return self._key() > other._key()

    def __ge__(self, other):
        return self._key() >= other._key()

class Student(ComparableMixin):
    def __init__(self, name, grade):
        self.name = name
        self.grade = grade

    def _key(self):
        return self.grade

alice = Student("Alice", 95)
bob = Student("Bob", 87)
print(alice > bob)             # True
print(alice >= bob)            # True
print(sorted([bob, alice]))    # Sorted by grade

7. Abstract Base Classes (ABCs)

Abstract base classes define interfaces that subclasses must implement. They enforce a contract, ensuring certain methods exist.

Why ABCs?

  • Enforce interfaces: Ensure subclasses implement required methods.
  • Documentation: ABCs clearly declare what a class should do.
  • Type checking: isinstance() works with registered ABCs.
  • Polymorphism: Code can accept any object that implements the interface.

abc.ABC and @abstractmethod

from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self):
        """Return the area of the shape."""
        pass

    @abstractmethod
    def perimeter(self):
        """Return the perimeter of the shape."""
        pass

    def describe(self):           # Concrete method (not abstract)
        return f"{self.__class__.__name__}: area={self.area():.2f}, perimeter={self.perimeter():.2f}"

# This will raise TypeError — can't instantiate abstract class
# shape = Shape()  # TypeError: Can't instantiate abstract class Shape

class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius

    def area(self):               # Must implement
        return 3.14159 * self.radius ** 2

    def perimeter(self):          # Must implement
        return 2 * 3.14159 * self.radius

class Rectangle(Shape):
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def area(self):
        return self.width * self.height

    def perimeter(self):
        return 2 * (self.width + self.height)

c = Circle(5)
r = Rectangle(4, 6)
print(c.describe())              # Circle: area=78.54, perimeter=31.42
print(r.describe())              # Rectangle: area=24.00, perimeter=20.00

Abstract Properties

from abc import ABC, abstractmethod

class Vehicle(ABC):
    @property
    @abstractmethod
    def fuel_type(self):
        """Return the fuel type."""
        pass

    @property
    @abstractmethod
    def max_speed(self):
        """Return the max speed."""
        pass

class ElectricCar(Vehicle):
    def __init__(self, speed=200):
        self._speed = speed

    @property
    def fuel_type(self):
        return "Electricity"

    @property
    def max_speed(self):
        return self._speed

car = ElectricCar(250)
print(car.fuel_type)             # Electricity
print(car.max_speed)             # 250

Concrete Methods in ABCs

ABCs can have concrete (non-abstract) methods that use abstract methods:

from abc import ABC, abstractmethod

class Database(ABC):
    @abstractmethod
    def connect(self):
        pass

    @abstractmethod
    def execute(self, query):
        pass

    def get_version(self):         # Concrete method
        result = self.execute("SELECT version()")  # Uses abstract methods
        return result

abc.register() — Virtual Subclasses

from abc import ABC, abstractmethod

class Drawable(ABC):
    @abstractmethod
    def draw(self):
        pass

class Line:
    """Not inheriting from Drawable, but can be registered."""
    def draw(self):
        return "Drawing a line"

# Register Line as a virtual subclass of Drawable
Drawable.register(Line)

line = Line()
print(isinstance(line, Drawable))   # True (even without inheritance!)
print(issubclass(Line, Drawable))   # True
⚠️ Virtual subclasses are not enforced: register() makes isinstance and issubclass return True, but Python does NOT check that the registered class actually implements the abstract methods. Use with care.

__subclasshook__ — Custom Subclass Checks

from abc import ABC, abstractmethod

class Sized(ABC):
    @abstractmethod
    def __len__(self):
        pass

    @classmethod
    def __subclasshook__(cls, C):
        if cls is Sized:
            if any("__len__" in B.__dict__ for B in C.__mro__):
                return True
        return NotImplemented

# list has __len__, so it's recognized as a Sized
print(isinstance([1, 2, 3], Sized))   # True
print(isinstance("hello", Sized))      # True

collections.abc — Built-in ABCs

from collections.abc import Iterable, Sequence, Mapping

# Check if objects implement common protocols
print(isinstance([1, 2, 3], Iterable))   # True
print(isinstance([1, 2, 3], Sequence))   # True
print(isinstance({"a": 1}, Mapping))     # True
print(isinstance("hello", Sequence))     # True
print(isinstance(42, Iterable))          # False

8. Duck Typing

Duck typing means an object's suitability is determined by the presence of certain methods and properties, not by its type. "If it walks like a duck and quacks like a duck, it's a duck."

Protocol-Based Polymorphism

class Dog:
    def speak(self):
        return "Woof"

class Cat:
    def speak(self):
        return "Meow"

class Duck:
    def speak(self):
        return "Quack"

# This function doesn't care about types — it only cares about the speak() method
def make_speak(animal):
    print(animal.speak())

make_speak(Dog())               # Woof
make_speak(Cat())               # Meow
make_speak(Duck())              # Quack

hasattr() and getattr()

def draw_shape(shape):
    if hasattr(shape, 'area') and callable(shape.area):
        print(f"Area: {shape.area()}")
    else:
        print("Cannot draw: no area() method")

class Circle:
    def __init__(self, r):
        self.r = r
    def area(self):
        return 3.14159 * self.r ** 2

class Square:
    def __init__(self, s):
        self.s = s
    def area(self):
        return self.s ** 2

draw_shape(Circle(5))           # Area: 78.53975
draw_shape(Square(4))           # Area: 16

ABCs as Formal Protocols

ABCs formalize duck typing by explicitly declaring the required interface:

from abc import ABC, abstractmethod

class Drawable(ABC):
    @abstractmethod
    def draw(self):
        pass

class Circle:
    def draw(self):
        return "O"

class Square:
    def draw(self):
        return "[]"

class NotDrawable:
    pass

def render(item: Drawable):
    """Accepts anything that implements Drawable."""
    print(item.draw())

render(Circle())                 # O
render(Square())                 # []
# render(NotDrawable())         # TypeError: Missing draw()

# Or use isinstance with register or __subclasshook__
Drawable.register(Circle)
Drawable.register(Square)
print(isinstance(Circle(), Drawable))  # True

When to Prefer Duck Typing vs Inheritance

ApproachWhen to Use
Duck typingWhen objects don't share a common ancestor but have compatible interfaces
InheritanceWhen objects share a true "is-a" relationship and common implementation
ABCsWhen you want to formalize the duck typing contract with enforcement
💡 Python's philosophy: Python favors duck typing. The built-in functions len(), iter(), str(), etc. all use duck typing — they call __len__, __iter__, __str__ without checking the type.

9. isinstance() and issubclass()

These built-in functions check type relationships in the inheritance hierarchy.

isinstance()

class Animal:
    pass

class Dog(Animal):
    pass

class Puppy(Dog):
    pass

d = Dog()
p = Puppy()

print(isinstance(d, Dog))       # True
print(isinstance(d, Animal))    # True (Dog inherits from Animal)
print(isinstance(d, Puppy))     # False

print(isinstance(p, Dog))       # True (Puppy inherits from Dog)
print(isinstance(p, Animal))    # True

# Tuple check — is it ANY of these types?
print(isinstance(d, (Dog, Cat, Animal)))  # True
print(isinstance(d, (int, str)))          # False

issubclass()

print(issubclass(Dog, Animal))   # True
print(issubclass(Puppy, Dog))    # True
print(issubclass(Puppy, Animal)) # True (transitive)
print(issubclass(Animal, Dog))   # False

print(issubclass(bool, int))     # True (bool is a subclass of int!)
print(issubclass(int, (int, str)))  # True

type() vs isinstance()

d = Dog()

# type() checks exact type
print(type(d) is Dog)            # True
print(type(d) is Animal)         # False (even though Dog inherits from Animal!)

# isinstance() checks the whole hierarchy
print(isinstance(d, Animal))     # True

# Prefer isinstance() — it respects inheritance
# Use type() only when you need exact type matching (rare)
⚠️ Don't use type() == for type checking: It breaks with subclasses. Always prefer isinstance() unless you have a specific reason to check exact types.

Edge Cases and Gotchas

# bool is a subclass of int
print(isinstance(True, int))     # True
print(issubclass(bool, int))     # True

# Everything is a subclass of object
print(isinstance(42, object))    # True
print(isinstance("hello", object))  # True

# None is an instance of NoneType
print(isinstance(None, type(None)))  # True
print(isinstance(None, object))      # True (NoneType is a subclass of object)

# Empty sequences
print(isinstance([], list))      # True
print(isinstance((), tuple))     # True
print(isinstance({}, dict))      # True

10. Practical Patterns

Template Method Pattern

The parent defines the algorithm skeleton, children fill in the steps:

from abc import ABC, abstractmethod

class DataProcessor(ABC):
    """Template method pattern — parent defines the algorithm."""

    def process(self):                 # Template method
        data = self.load_data()
        cleaned = self.clean(data)
        result = self.analyze(cleaned)
        self.report(result)
        return result

    def load_data(self):               # Concrete method (default)
        return [1, 2, 3, 4, 5]

    @abstractmethod
    def clean(self, data):             # Abstract — children must implement
        pass

    @abstractmethod
    def analyze(self, data):           # Abstract — children must implement
        pass

    def report(self, result):          # Concrete method (default)
        print(f"Result: {result}")

class AverageProcessor(DataProcessor):
    def clean(self, data):
        return [x for x in data if isinstance(x, (int, float))]

    def analyze(self, data):
        return sum(data) / len(data) if data else 0

class SumProcessor(DataProcessor):
    def clean(self, data):
        return [x for x in data if x > 0]

    def analyze(self, data):
        return sum(data)

avg = AverageProcessor()
print(avg.process())                  # 3.0

total = SumProcessor()
print(total.process())                # 15

Composition vs Inheritance

When to use which:

Use Inheritance WhenUse Composition When
Clear "is-a" relationship"Has-a" relationship

Polymorphism is neededFlexibility in swapping components
Examples: Dog is an Animal, SavingsAccount is an AccountExamples: Car has an Engine, Computer has a CPU
# Composition: Car HAS an Engine
class Engine:
    def __init__(self, horsepower):
        self.horsepower = horsepower

    def start(self):
        return f"Engine with {self.horsepower}hp started"

class Car:
    def __init__(self, make, model, engine):
        self.make = make
        self.model = model
        self.engine = engine   # Composition — not inheritance

    def start(self):
        return f"{self.make} {self.model}: {self.engine.start()}"

car = Car("Toyota", "Camry", Engine(203))
print(car.start())            # Toyota Camry: Engine with 203hp started

Liskov Substitution Principle (LSP)

Subclasses should be substitutable for their parent classes without breaking the program:

class Bird:
    def move(self):
        return "Moving"

class FlyingBird(Bird):
    def move(self):
        return "Flying"

class Penguin(Bird):       # Penguins are birds but don't fly
    def move(self):
        return "Swimming"

# Both work — LSP is satisfied
def describe_movement(bird: Bird):
    print(bird.move())

describe_movement(FlyingBird())   # Flying
describe_movement(Penguin())      # Swimming
💡 LSP violation example: If a Square inherits from Rectangle but overrides width/height to always be equal, calling code that sets width independently will break. This is why inheritance must model true "is-a" relationships.
